## Research question

At a fixed analyst alert budget, how do unsupervised anomaly detection and
supervised tabular models compare on chronologically held-out AML transactions,
and does adding strictly historical account/network context improve detection?

Primary contribution: a transparent, reproducible comparison and an interactive
model evaluation/triage demo. Do not claim a novel state-of-the-art architecture.

## Data strategy

Primary planned benchmark: the public IBM AML-Data dataset. The official project
describes it as completely synthetic, generated by a virtual world of agents;
it is not anonymized real customer data. The repository code license is
Apache-2.0; the data has separate CDLA-Sharing-1.0 terms. The official README
links to Kaggle and Box. Download, exact version, byte size, checksum, class
counts and schema have not yet been verified locally.

Data acquisition is a blocking gate for claims about IBM benchmark performance.
Record the actual downloaded version and its provenance before experiments.
Use chronological windows rather than a randomly shuffled development subset.
If resource limits require a subset, freeze its sampling/window definition and
report it prominently. Check that every partition contains sufficient positives.
Do not publish licensed data extracts until applicable redistribution terms have
been checked. Code and documentation licenses do not override data licenses.

A small original simulator may supply unit-test fixtures and demo scenarios.
Its results must be labeled simulation-only and kept separate from IBM results.
If IBM acquisition fails, report that blocker; never substitute fixtures silently.
Elliptic may be evaluated as a later secondary benchmark after access, feature
provenance and license verification; it is not required for the initial release.
Never use TD data, internal documents, credentials, processes or client records.

## Architecture

Training and evaluation: Python, pandas, NumPy and scikit-learn, with pinned
dependencies and explicit experiment configuration. Start with a transparent
rule baseline, Logistic Regression, Isolation Forest and a tree ensemble.
Use tabular-only versus tabular-plus-causal-context ablations. Keep GNNs as a
later experiment justified by results and compute availability.

Interface: React + TypeScript, with separate views for Demo, Methodology and
Results. Show transactions, ranked alerts, historical context, local explanation
and threshold/budget controls. Methodology includes source data, licenses,
features, libraries, exact training procedure and limitations. Results includes
measured metrics, PR curves and model comparisons with experiment identifiers.

Inference: export a compact supported model and preprocessing contract to JSON
or another browser-compatible format. Verify Python/browser output parity on
frozen fixtures before release. Use actual trained weights; never hard-code risk
outputs. If a selected model cannot be exported faithfully within resource
limits, use a supported alternative or an appropriate inference service and
document the architecture change.

Demo scenarios carry the historical context needed by the model. An arbitrary
standalone transaction cannot supply rolling account features. Prefer preset
public/synthetic scenarios initially; any CSV upload is processed locally and
requires a documented schema, size limit and validation. No persistence by default.

## ML acceptance criteria

- Freeze train/validation/test time cutoffs before tuning. Preserve identical
  timestamp groups; specify treatment of same-time edges and late records.
- Fit preprocessing on training only. Compute historical features using strictly
  prior events; modifying future rows must not change earlier feature values.
- Labels, IDs, generator typology tags and post-event outcomes must not become
  accidental model inputs. Account IDs may index history, not encode labels.
- Freeze hyperparameters and thresholds using validation only. Evaluate the
  held-out test set after choices are fixed; do not tune after viewing test scores.
- Describe whether accounts repeat across windows. A separate account holdout
  is needed for claims about unseen-account generalization.
- Report class prevalence, Average Precision (label it AP rather than conflating
  it with trapezoidal PR-AUC), ROC-AUC as secondary, precision/recall at a fixed
  threshold and at alert budgets, and confusion matrices.
- Distinguish adaptive top-k ranking from a fixed validation-derived threshold;
  test budgets cannot use test labels. Quantify variation across repeated runs
  and temporal blocks when sample sizes support meaningful uncertainty estimates.
- Unknown labels are excluded or handled as unknown, never silently normal.
- Isolation Forest outputs are anomaly scores, not laundering probabilities.
  Supervised score calibration requires its own disjoint validation protocol.
- Explain model sensitivity or local contributions without causal claims.
- Record configuration, seed, dependency versions, data/model hashes and commit.

## Web/security acceptance criteria

- Verify model/preprocessing parity including missing, unseen and extreme inputs.
- Handle malformed CSV, duplicate events, invalid times, nonfinite amounts,
  schema mismatches and unsupported categories with clear errors.
- Validate input size and computation limits; render input as text, never HTML.
- Show dataset identity, model version and applicable limitations alongside results.
- Audit keyboard interaction, error/loading/empty states and mobile layout.
- Check tracked source for secrets and private material; keep raw datasets and
  temporary files out of commits as required by size/privacy/license constraints.
- CI must run meaningful Python tests, frontend checks and parity tests. Report
  remote CI separately from local checks; do not claim a workflow passed merely
  because its YAML exists.
- Deployment must serve the implemented trained model and measured report.
  A simulation-only prototype must be described as such in the UI and release.
